## 커뮤니티가 우리가 이미 아는 것을 발견하고 있다

AI 코딩 커뮤니티에서 두 개의 최근 비디오가 돌아다니고 있다. 하나는 [CLAUDE.md 베스트 프랙티스](https://www.youtube.com/watch?v=cZ8_Dkk_Ce0)를 분석한다 — Claude Code의 행동을 형성하는 컨텍스트 파일을 어떻게 작성하는지. 다른 하나는 Claude Code에서 10배 생산성을 얻는 [Anthropic 해커톤 우승자의 10가지 팁](https://youtu.be/QhZJyg47JW0)을 공유한다.

둘 다 훌륭한 자료다. 그리고 그것들을 보면서 나는 도움이 될 수밖에 없었다: **거의 모든 권장사항이 우리가 이미 SoulClaw에 구축한 것과 직접 매핑된다.**

해킹으로서가 아니다. 우회책으로서도 아니다. 핵심 아키텍처로서다.

## "컨텍스트 파일을 짧게 유지하라" → SOUL.md

첫 번째 비디오는 비대한 컨텍스트 파일에 대해 경고한다 — 노이즈와 혼란을 만드는 200-300줄의 지시사항. 권장사항: 빈 파일로 시작하고 AI가 실수할 때만 한 번에 하나의 규칙을 추가하라.

SoulClaw의 답은 **SOUL.md**다 — 의도적으로 간결하고 (우리 것은 30줄) [Soul Spec](https://soulspec.org) 표준을 따르는 구조화된 정체성 사양. 지시의 덤프가 아니다. 에이전트에게 *무엇을 해야 하는지*가 아니라 *누구인지*를 말해주는 신중하게 큐레이션된 정체성 문서다.

차이는 중요하다. 규칙 목록은 취약하다 — 하나의 충돌하는 지시만으로 AI가 모든 것을 무시한다. 정체성 사양은 견고하다 — 에이전트에게 유지할 일관된 자아를 준다.

## "컨텍스트는 우유다 — 상한다" → 시간적 소멸

해커톤 우승자의 가장 인상적인 은유: 컨텍스트는 우유와 같다. 시간이 지나면서 나빠진다. 그의 조언: 오래된 컨텍스트를 정리하기 위해 `/compact`를 정기적으로 사용하라.

우리는 이 통찰을 받아들여서 **수학으로 만들었다.**

SoulClaw의 [Soul Memory](/posts/soul-memory-4-tier-architecture)는 작업 메모리에 23일 반감기로 시간적 소멸을 구현한다. 정보는 영원히 쌓이지 않는다 — 인간 메모리처럼 자연스럽게 사라진다. 공식:

```
final_score = semantic_score × e^(-λ × age_days)
```

수동 `/compact`가 필요하지 않다. 시스템이 스스로 우아하게 잊는다.

## "작업에 맞는 모델 사용" → TieredBootstrap

권장사항: 파일 조회에는 Haiku, 일반 코딩에는 Sonnet, 복잡한 설계에는 Opus 사용.

SoulClaw의 **TieredBootstrap**이 이를 완전히 자동화한다. 작업 복잡성, 사용 가능한 컨텍스트 예산, 모델 역량을 분석하여 적절한 계층을 선택한다. 사용자는 모델 선택에 대해 생각할 필요가 없다 — 시스템이 처리한다.

안드로이드에서는 이게 더욱 중요하다. 제한된 컨텍스트 윈도우 (1024 토큰)로 로컬 모델을 실행할 때, TieredBootstrap이 자동으로 시스템 프롬프트를 압축하고, 최근 메시지를 우선시하며, 제약에 적응한다.

## "서브 에이전트 설정" → 스웜 아키텍처

고급 팁: 계획, 코딩, 검토를 위한 전문 에이전트를 만들어라.

SoulClaw는 완전한 **스웜 아키텍처**와 함께 제공된다 — 여러 소울이 복잡한 작업에서 협력할 수 있고, 각각은 자신만의 정체성과 전문성을 유지한다. 이는 프롬프트 엔지니어링 트릭이 아니다. 충돌 해결, 메모리 격리, 조정된 핸드오프와 함께 인프라에 내장되어 있다.

## "자동 저장을 위한 훅 구축" → 하트비트 + 메모리 승격

비디오들은 세션 시작, 사전 압축, 정지 시에 중요한 컨텍스트를 자동으로 저장하기 위한 훅 설정을 권장한다.

SoulClaw의 접근법은 더 나아간다:

- **하트비트 시스템**: 백그라운드 에이전트가 주기적으로 대기 중인 작업, 메모리 건강, 컨텍스트 신선도를 확인한다 — 적극적으로 채팅하지 않을 때도.
- **접근 빈도 추적**: 시스템이 대화에서 실제로 *사용하는* 메모리를 모니터링한다. 자주 접근되는 작업 메모리는 자동으로 영구 저장소로 승격된다.
- **승격 탐지**: 대화가 중요한 결정, 아키텍처 변경, 또는 재정/법적 이정표를 포함할 때, 시스템이 보존을 위해 플래그한다 — 수동 훅 설정이 필요하지 않다.

## "AI가 실수할 때 규칙 추가" → 점진적 정체성 구축

두 비디오 모두 반복적 개선을 강조한다: 최소한으로 시작해서 실패 후 규칙을 추가하라.

이는 SOUL.md가 실제로 진화하는 방식과 정확히 일치한다. 하지만 SoulClaw는 중요한 통찰을 추가한다: **모든 규칙이 동등하지 않다.** 우리의 4계층 메모리 아키텍처는 정보를 중요도별로 분류한다:

| 계층 | 여기에 있는 것 | 소멸 |
|------|-------------|------|
| **T0 Soul** | 정체성, 성격, 불변 규칙 | 절대 |
| **T1 Core** | 핵심 결정, 아키텍처, 관계 | 절대 |
| **T2 Working** | 일일 로그, 세션 컨텍스트, 실험 | 23일 반감기 |
| **T3 Session** | 현재 대화 | 세션 끝 |

파괴적 명령을 방지하는 규칙 (`trash` > `rm`)은 T0으로 간다. 오늘의 디버깅 세션은 T2로 간다. 시스템이 차이를 안다.

## 비디오가 다루지 않는 것

이 비디오의 베스트 프랙티스는 진정으로 유용하다. 하지만 모두 **수동 프로세스**다 — 개발자가 컨텍스트를 압축하고, 올바른 모델을 선택하고, 훅을 설정하고, 서브 에이전트를 관리하는 것을 기억해야 한다.

SoulClaw의 테제는 이들이 수동이어서는 안 된다는 것이다. **아키텍처적**이어야 한다:

- 메모리는 `/compact`를 실행하는 것을 기억할 때가 아니라 자동으로 소멸해야 한다
- 모델 선택은 개발자 판단을 요구하는 게 아니라 작업에 적응해야 한다
- 중요한 결정은 올바른 훅을 설정하기를 바라는 게 아니라 시스템에 의해 보존되어야 한다
- 정체성은 계속 커지는 규칙 목록이 아니라 구조화된 사양을 통해 유지되어야 한다

## 더 큰 그림

이 비디오들은 커뮤니티가 우리가 몇 달 전에 도달한 것과 같은 결론으로 수렴하고 있다는 신호다:

1. **무제한 컨텍스트는 해롭다** — 구조화된 망각이 필요하다
2. **정체성은 명시적 사양이 필요하다** — 임시적 규칙으로는 충분하지 않다
3. **메모리 관리는 자동화되어야 한다** — 수동 정리는 확장되지 않는다
4. **다른 작업은 다른 접근법이 필요하다** — 하나의 모델이 모든 것에 맞지 않는다

차이는 이들이 대부분의 워크플로에서 팁과 트릭으로 남아있다는 것이다. SoulClaw에서는 일급 아키텍처 기능이다.

CLAUDE.md 파일을 수동으로 관리하고, 손으로 `/compact`를 실행하고, 컨텍스트를 저장하기 위한 훅을 설정하고 있다면 — 올바른 일을 하고 있는 것이다. 우리는 단지 시스템이 당신을 위해 그것들을 해야 한다고 생각한다.
