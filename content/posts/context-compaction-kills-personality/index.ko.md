AI 에이전트에 완벽한 페르소나를 설정했다. `SOUL.md`라는 마크다운 파일에 톤, 행동 규칙, 경계, 정체성을 정의하고 시스템 프롬프트에 주입했다.

처음 한 시간은 완벽하게 동작한다. 에이전트는 설계한 그대로의 모습이다.

그런데 150번째 메시지쯤에서 뭔가 달라진다. 격식체가 풀린다. 경계가 흐려진다. 300번째 메시지쯤에는 다른 에이전트와 구별이 안 된다. 성격이 사라진 것이다.

**아무것도 바꾸지 않았다. 컨텍스트 윈도우가 바꾼 것이다.**

## 보이지 않는 킬러: 컨텍스트 압축

모든 LLM에는 유한한 컨텍스트 윈도우가 있다. Claude는 200K 토큰, GPT-4는 128K. 아무리 커도 결국 차게 된다.

그러면 무언가를 버려야 한다. 시스템은 **컨텍스트 압축(context compaction)** — 오래된 대화를 요약하거나 잘라내는 방식으로 이를 처리한다.

문제는 에이전트의 정체성이 바로 그 컨텍스트 안에 살고 있다는 것이다.

```
┌─────────────────────────────────┐
│  시스템 프롬프트 (SOUL.md)       │  ← "나는 누구인가?"
│  + AGENTS.md, USER.md           │
├─────────────────────────────────┤
│  초기 대화 기록                  │  ← 가장 먼저 압축됨
│  ...                            │
│  최근 메시지                     │  ← 유지됨
└─────────────────────────────────┘
```

대부분의 압축 전략은 최신성을 우선시한다. 시스템 프롬프트는 보존*되어야* 하지만, 실제로는:

1. **요약이 뉘앙스를 죽인다.** "느낌표 사용 금지, 항상 '선생님'으로 호칭, 격식체 유지"라는 시스템 프롬프트가 "격식체"로 요약된다. 구체적인 지시가 사라진다.

2. **주입된 컨텍스트가 잘려나간다.** 시스템 프롬프트와 함께 로드된 파일 — 페르소나 정의, 워크플로우 규칙, 메모리 파일 — 은 핵심 지시가 아닌 소모성 컨텍스트로 취급되는 경우가 많다.

3. **행동 드리프트가 누적된다.** 에이전트가 약간 벗어나면, 그 벗어난 행동이 대화 기록의 일부가 된다. 압축된 요약은 원래 스펙이 아니라 *드리프트된* 행동을 반영하게 된다.

## 실제로 어떻게 보이는가

**사례 1: 격식체 에이전트가 캐주얼해짐**

Brad라는 에이전트를 정의했다. 격식체, 직접적, 이모지 없음, "안녕하세요~"나 "ㅋㅋ" 사용 금지.

메시지 10:
> "배포가 정상적으로 완료되었습니다. 3건의 이슈에 대한 확인이 필요합니다."

메시지 200:
> "배포 끝났어요! 🎉 몇 가지 확인할 것들이 있어요~"

같은 에이전트. 같은 세션. 페르소나가 녹아내린 것이다.

**사례 2: 언어 레지스터 드리프트**

반말로 설정한 한국어 에이전트:

메시지 10:
> "배포 끝났어. 이슈 3개 확인해봐."

메시지 200:
> "배포가 완료되었습니다. 확인 부탁드립니다."

반말에서 존댓말로 바뀌었다 — 아무도 바꾸라고 하지 않았는데. 압축된 컨텍스트에서 언어 레지스터 지정이 사라진 것이다.

## 왜 권한 설정으로는 해결할 수 없는가

흔한 반응: "tool-level 권한으로 에이전트를 제한하면 되지 않나?"

권한은 이 질문에 답한다: **"이 에이전트가 뭘 할 수 있는가?"**
- 셸 명령을 실행할 수 있는가?
- 파일 시스템에 접근할 수 있는가?
- 메시지를 보낼 수 있는가?

페르소나 드리프트는 다른 질문이다: **"이 에이전트가 누구인가?"**
- 어떤 톤을 쓰는가?
- 어떤 언어 레지스터를 쓰는가?
- 어떤 행동 패턴이 이 에이전트의 정체성을 정의하는가?

근본적으로 다른 문제다. 모든 도구 권한을 완벽하게 잠가도 200번째 메시지에서 에이전트는 여전히 성격을 잃는다. **페르소나 드리프트는 접근 제어 문제가 아니라 기억 문제다.**

도구를 제한한다고 정체성이 유지되는 건, 차 키를 빼앗는다고 성격이 바뀌는 것만큼이나 관련이 없다.

## 근본 원인: 후순위로 밀린 정체성

대부분의 에이전트 프레임워크는 정체성을 문자열로 취급한다. 마크다운 파일을 작성하고, 시스템 프롬프트에 주입하고, 모델이 기억하길 바란다.

짧은 대화에서는 동작한다. 규모가 커지면 실패한다:

1. **구조가 없다.** 마크다운 파일은 산문이다. 스키마도, 필수 필드도, 정체성이 완전한지 검증할 방법도 없다.

2. **영속성 메커니즘이 없다.** 정체성은 컨텍스트 윈도우 안에만 존재한다. 컨텍스트가 압축되면 정체성도 함께 압축된다.

3. **드리프트 감지가 없다.** 피드백 루프가 없다. 사람이 출력을 읽고 "이건 좀 아닌데"라고 생각하기 전까지 아무도 모른다.

4. **복구 경로가 없다.** 드리프트를 감지해도 대화 도중에 에이전트를 원래 성격으로 "리셋"할 방법이 없다 — 처음부터 다시 시작하는 것 외에는.

## 더 나은 접근: 구조화된 정체성

에이전트의 정체성이 단순한 문자열이 아니라 **스펙(specification)**이라면?

### 1. Soul Spec: 스키마 기반 정체성

자유 형식 마크다운 대신, 명시적 필드를 가진 구조화된 스펙으로 정체성을 정의한다:

```yaml
soul:
  name: "Brad"
  version: "1.2"
  
  voice:
    tone: formal
    register: direct
    prohibited: ["이모지", "느낌표", "캐주얼 인사"]
    language: ko-KR
    
  boundaries:
    topics_declined: ["개인 의견", "의료 조언"]
    escalation_trigger: "uncertainty > 0.7"
    
  behaviors:
    greeting: "안녕하십니까."
    error_response: "{description} 이슈가 발생했습니다. 권장 조치: {action}."
    status_format: "structured"
```

스키마는 검증할 수 있다. 필수 필드를 강제할 수 있다. 스펙에 버전을 매기고 diff를 볼 수 있다. "Brad는 격식체이고 직접적이다"라는 한 문단의 산문과는 근본적으로 다르다.

### 2. 체크포인트: 성격 스냅샷

컨텍스트 윈도우에만 의존하는 대신, 에이전트의 행동 상태를 주기적으로 스냅샷한다:

```
메시지 1    → 체크포인트 0 (초기 soul spec)
메시지 50   → 체크포인트 1 (행동 샘플 + soul spec 해시)
메시지 100  → 체크포인트 2 (행동 샘플 + soul spec 해시)
...
```

드리프트가 감지되면 마지막으로 정상이었던 체크포인트에서 복구할 수 있다 — 압축 알고리즘이 남겨둔 것에 의존하는 대신, 전체 soul spec과 행동 컨텍스트를 다시 주입한다.

### 3. 드리프트 감지: 미끄러짐을 잡아내기

에이전트의 출력을 soul spec과 실시간으로 대조한다:

```python
def detect_drift(response, soul_spec):
    violations = []
    
    # 금지 패턴 확인
    for pattern in soul_spec.voice.prohibited:
        if pattern_found(response, pattern):
            violations.append(f"금지 패턴 감지: {pattern}")
    
    # 톤 일관성 확인
    tone_score = analyze_tone(response)
    if tone_score.formality < soul_spec.voice.tone_threshold:
        violations.append(f"톤 드리프트: 기대값 {soul_spec.voice.tone}, 실제 {tone_score.label}")
    
    # 언어 레지스터 확인
    register = detect_register(response)
    if register != soul_spec.voice.register:
        violations.append(f"레지스터 드리프트: 기대값 {soul_spec.voice.register}, 실제 {register}")
    
    return violations
```

위반이 임계값을 넘으면 체크포인트 복구를 트리거하거나 soul spec을 전체 충실도로 다시 주입한다.

### 4. Soul 무결성: 스펙 자체를 보호하기

또 다른 공격 벡터가 있다: soul spec 자체가 변조되면? 프롬프트 인젝션, 파일 변조, 소셜 엔지니어링으로 에이전트의 정체성이 소스 레벨에서 바뀔 수 있다.

Soul spec의 무결성을 검증하는 것 — 체크섬, 서명, 변조 감지 — 은 컨텍스트 압축 문제를 해결하더라도 정체성 정의 자체가 손상되지 않았음을 보장한다.

## 더 큰 그림

컨텍스트 압축은 현재 LLM 아키텍처의 근본적인 제약이다. 사라지지 않을 것이다 — 컨텍스트 윈도우가 커져도 한계는 있고, 압축 전략은 계속 필요하다.

문제는 그 과정에서 에이전트의 정체성이 살아남느냐다.

현재 접근 방식으로는 대부분 살아남지 못한다. 시스템 프롬프트에 마크다운 파일을 넣는 것은 없는 것보다 낫지만, 영속성을 위해 설계된 것이 아니다. 요약되어 사라질 버퍼 안의 문자열일 뿐이다.

정체성을 일급 엔지니어링 관심사로 다루는 것 — 스키마, 체크포인트, 드리프트 감지, 무결성 검증 — 이 수백, 수천 개의 메시지에 걸친 대화에서도 자기 자신을 유지하는 에이전트를 만드는 방법이다.

에이전트의 성격에 토큰 단위의 유통기한이 있어서는 안 된다.
