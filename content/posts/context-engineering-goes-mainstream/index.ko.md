## 한 줄 프롬프트의 시대가 끝나다

수년간 "프롬프트 엔지니어링"은 모두가 이야기하는 핵심 역량이었습니다. 완벽한 지시문을 작성하고, 적절한 예시를 넣고, temperature를 조절하면 AI가 원하는 결과를 내놓았습니다.

AI가 텍스트 입력 → 텍스트 출력 상자였을 때는 그것으로 충분했습니다.

하지만 AI 에이전트가 도구를 사용하고, 세션 간 메모리를 유지하며, 다단계 의사결정을 하고, 수 시간 동안 자율적으로 작동하는 지금은 다릅니다. **단일 프롬프트로 시스템을 통제할 수 없습니다.**

## 무엇이 바뀌었는가

**Prompt Engineering**은 단일 입력 문자열을 최적화합니다.
- "이 문서를 3개 요점으로 요약해줘."
- "시니어 개발자처럼 이 코드를 리뷰해줘."
- 범위: 한 턴, 한 작업, 한 응답.

**Context Engineering**은 전체 정보 환경을 설계합니다.
- 에이전트가 접근할 수 있는 메모리는?
- 어떤 도구를 어떤 순서로 사용할 수 있는가?
- 모호한 상황에서의 의사결정 규칙은?
- 자기 출력을 어떻게 검증하는가?
- 실패 시 어떻게 대응하는가?

비유하자면: 프롬프트 엔지니어링은 SQL 쿼리 하나를 튜닝하는 것. Context Engineering은 데이터베이스 스키마, 인덱스, 쿼리 옵티마이저, 접근 제어를 함께 설계하는 것입니다.

## 버즈워드가 아니다 — 모든 곳에서 등장하고 있다

Anthropic은 ["Effective Context Engineering for AI Agents"](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) 아티클에서 이 용어를 정의하며 다음과 같은 문제를 식별했습니다:
- **Context rot**: 긴 대화에서 에이전트 컨텍스트가 열화
- **Tool confusion**: 명확한 행동 규칙 없이 잘못된 도구 선택
- **Memory management**: 무엇을 기억하고, 잊고, 우선시할 것인가

하지만 이제 AI 연구소만의 이야기가 아닙니다.

최근 팔란티어의 AI 인프라를 분석한 투자 리포트에서, Context Engineering이 핵심 시스템 설계 요소로 등장했습니다 — 피드백 메커니즘, 물리시뮬레이터, 교차검증과 나란히. 투자 분석가들이 이 용어를 사용하기 시작하면, 더 이상 학술적 개념이 아닙니다. 인프라입니다.

패턴은 명확합니다:
- **AI 연구** → Anthropic이 Context Engineering을 학문으로 정의
- **기업 AI** → 팔란티어의 아키텍처가 이 렌즈로 분석됨
- **개발자 도구** → MCP, 에이전트 프레임워크, 워크플로우 시스템 모두 컨텍스트 문제의 조각들을 다룸
- **프로덕션 시스템** → 팀마다 매 프로젝트에서 처음부터 커스텀 컨텍스트 파이프라인을 구축

## 진짜 문제: 표준이 없다

아무도 이야기하지 않는 것: **모두가 Context Engineering을 하고 있지만, 모두 다르게 하고 있습니다.**

- A사는 47개 변수가 있는 커스텀 시스템 프롬프트 템플릿
- B사는 에이전트 프레임워크에 도구 선택 규칙을 하드코딩
- 개발자 C는 프로젝트 간에 복사하는 `.cursorrules` 파일 유지
- 개발자 D는 에이전트의 성격과 워크플로우를 정의하는 SOUL.md 사용

이 모든 것이 Context Engineering입니다. 하나도 상호 운용되지 않습니다. 검증 가능하지 않습니다. 공유 가능하지 않습니다.

Docker가 배포 스크립트를 표준화하기 전, 모두가 자체 배포 스크립트를 가지고 있던 초기 컨테이너화 시대와 같습니다.

## Soul Spec의 위치

Soul Spec은 **Context Engineering 표준**입니다 — 이 버즈워드보다 먼저 존재했을 뿐입니다.

소울은 AI 에이전트의 완전한 행동 컨텍스트를 정의합니다:

| 레이어 | Prompt Engineering | Context Engineering (Soul Spec) |
|--------|-------------------|-------------------------------|
| **목소리** | "격식체로 답변해" | 톤, 스타일, 언어 규칙이 있는 페르소나 |
| **의사결정** | "Python을 선호해" | 우선순위와 대안이 있는 행동 규칙 |
| **워크플로우** | "먼저 분석, 그다음 코딩" | 검증이 포함된 다단계 실행 패턴 |
| **도구** | "검색 도구를 써" | 도구 선호도, 선택 기준, 재시도 로직 |
| **메모리** | 해당 없음 | 무엇을 기억하고, 참조하고, 무시할지 |
| **보안** | "유해하지 마" | 보안 스캔된 행동 규칙 (SoulScan) |

소울을 적용하면, 더 나은 프롬프트를 쓰는 것이 아닙니다. **완전한 Context Engineering 패키지를 설치**하는 것입니다 — 프레임워크 간 이식 가능하고, 보안 검증 가능하며, 다른 사람과 공유 가능합니다.

## 왜 지금 중요한가

세 가지 트렌드가 수렴하고 있습니다:

**1. 에이전트가 자율화되고 있다.** 수 시간 동안 실행되고, 수십 개 도구를 사용하며, 사람이 실시간으로 검토하지 않는 결정을 내립니다. 표준화된 컨텍스트 없이는 모든 에이전트가 블랙박스입니다.

**2. 재현성이 요구사항이 되고 있다.** 기업은 같은 에이전트가 매번 같은 품질을 내기를 원합니다. 이를 위해 표준화된 행동 규칙이 필요하지, 영리한 일회성 프롬프트가 아닙니다.

**3. 나쁜 컨텍스트의 비용이 보인다.** 에이전트가 잘못된 도구를 선택하거나, 워크플로우 중 할루시네이션을 일으키거나, 톤이 갑자기 바뀌면 — 근본 원인은 거의 항상 컨텍스트이지 모델 능력이 아닙니다.

## 비유

| 시대 | 문제 | 임시 해결책 | 표준 |
|------|------|-----------|------|
| 2000년대 | 배포 혼란 | 커스텀 스크립트 | Docker / Kubernetes |
| 2010년대 | API 불일치 | 프로젝트별 계약 | OpenAPI / REST 관례 |
| 2020년대 | AI 행동 혼란 | 커스텀 시스템 프롬프트 | **Context Engineering 표준** |

우리는 AI 행동 관리의 "커스텀 스크립트" 단계에 있습니다. Soul Spec은 표준화가 불가피하다는 데 베팅하고 있습니다.

## 다음은

Context Engineering은 일급 학문이 될 것입니다 — 프롬프트 엔지니어링의 하위 카테고리가 아니라, 후속 개념으로. 문제는 이것이 일어나느냐가 아니라, 누가 표준을 만드느냐입니다.

인프라가 형성되고 있습니다:
- **오픈 스펙** — Soul Spec은 7개 이상의 프레임워크에서 작동 (ChatGPT, Claude, Cursor, Windsurf, OpenClaw 등)
- **커뮤니티 라이브러리** — [ClawSouls](https://clawsouls.ai)에서 80개 이상의 사전 구축된 컨텍스트 패키지
- **보안 검증** — SoulScan이 배포 전 행동 규칙의 악성 패턴 검사
- **멀티플랫폼 배포** — 같은 소울, 같은 품질, 어떤 프레임워크든

Prompt Engineering이 시작이었습니다. Context Engineering이 우리가 가는 곳입니다.
