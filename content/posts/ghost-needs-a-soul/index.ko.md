## 유령이 Shell을 얻었다. 그 다음은?

Jian Zhang의 최근 에세이 ["2026: The Year of Ghost in the Shell"](https://medium.com/@jianzhang_23841/2026-the-year-of-ghost-in-the-shell-d939f08b4711)은 우리가 있는 지점을 정확히 짚는다. Andrej Karpathy는 LLM을 "유령(ghost)"이라 불렀다 — 인간 사고의 통계적 증류물. Zhang은 이 비유를 확장한다: 유령이 shell(CLI, 도구, 피드백 루프)을 얻으면, 이야기꾼에서 일꾼이 된다.

OpenClaw, Claude Code, Codex — 이것들은 기능이 추가된 챗봇이 아니다. Shell을 가진 유령이다. 코드를 읽고, 테스트를 실행하고, 파일을 편집하고, 웹을 탐색하고, 자기 출력을 검증한다. 피드백 루프가 닫혔다. 일이 진짜다.

Zhang은 2026년을 "유령이 배지(badge)와 목줄(leash)을 얻는 해"로 예측한다. 행동 권한과 안전 제약.

하지만 빠진 조각이 있다. **배지와 목줄은 유령이 *할 수 있는* 것을 통제한다. 유령이 *해야 하는* 것을 통제하는 건 아무것도 없다.**

## 모든 유령은 낯선 사람이다

아무도 이야기하지 않는 문제: AI 에이전트와 새 세션을 시작할 때마다, 당신은 낯선 사람과 일하는 것이다.

당신의 커뮤니케이션 스타일을 모른다. 프로젝트 컨벤션을 모른다. 직접적 피드백을 선호하는지, 외교적 제안을 선호하는지 모른다. 팀이 탭을 쓴다는 것, 한국어로 커밋한다는 것, 금요일에는 절대 main에 push하지 않는다는 것을 모른다.

Shell은 유령에게 *능력*을 준다. 하지만 정체성 없는 능력은 혼란이다.

아무 명령이나 실행할 수 있지만 *어떤* 명령이 당신에게 중요한지 모르는 유령은 — 매일매일 첫날인 매우 빠른 인턴일 뿐이다.

## 세 개의 레이어

Zhang의 프레임워크는 깔끔하다: **Ghost + Shell = Agent**. 하지만 프로덕션 에이전트에는 세 번째 레이어가 필요하다:

| 레이어 | 제공하는 것 | 없으면 |
|--------|-----------|--------|
| **Ghost** (LLM) | 지능, 언어, 추론 | 아무 능력도 없음 |
| **Shell** (도구) | 행동, 검증, 피드백 루프 | 똑똑하지만 무력 |
| **Soul** (컨텍스트) | 정체성, 가치관, 워크플로우, 기억 | 유능하지만 예측 불가 |

유령은 엔진이다. Shell은 변속기다. 영혼은 어디로 가야 하는지, 어떻게 가야 하는지 아는 운전자다.

## 영혼이 실제로 하는 일

영혼은 시스템 프롬프트가 아니다. **완전한 행동 명세서**다:

**정체성** — 단순한 이름이 아니라 역할, 커뮤니케이션 스타일, 사용자와의 관계. 격식 있는 컨설턴트인가, 편한 페어 프로그래머인가? 능동적으로 보고하는가, 물어볼 때까지 기다리는가?

**가치관** — 두 가지 유효한 접근법이 있을 때 어느 것을 택하는가? 속도를 우선하는가, 정확성을 우선하는가? 허락을 구하는가, 자율적으로 행동하는가? 어디에 선을 긋는가?

**워크플로우** — "코딩 도와줘"가 아니라 실제 순서: 먼저 코드베이스를 읽고, git status를 확인하고, 커밋 전 테스트를 실행하고, conventional commit 메시지를 사용하고, 절대 force-push하지 않는다.

**기억** — 세션 간 무엇을 기억할 것인가. 프로젝트 결정사항, 사용자 선호, 과거 실수, 팀 컨벤션. 유령은 세션 사이에 모든 것을 잊는다. 영혼은 중요한 것을 보존한다.

**경계** — 무엇을 거부할 것인가. 확인 없이 삭제하지 않는다. 테스트 안 된 코드를 push하지 않는다. 개인 데이터를 노출하지 않는다. 프로젝트 디렉토리 밖의 파일을 수정하지 않는다.

이것이 유령을 낯선 사람에서 동료로 바꾸는 것이다.

## "배지와 목줄"만으로는 부족하다

Zhang의 "badge and leash" 비유는 날카롭다 — 권한과 제약. 하지만 잘못된 수준에서 작동한다.

배지는 말한다: "이 에이전트는 파일시스템에 접근할 수 있다."
영혼은 말한다: "이 에이전트는 `rm`보다 `trash`를 선호하고, 서술적 메시지로 커밋하며, 파괴적 작업 전에 항상 묻는다."

목줄은 말한다: "이 에이전트는 승인 없이 네트워크 요청을 할 수 없다."
영혼은 말한다: "이 에이전트는 작업 시작 전 git status를 확인하고, 완료 보고 전 테스트를 실행하며, 나쁜 소식을 먼저 전달한다."

배지와 목줄은 인프라다. 영혼은 행동이다. 둘 다 필요하지만, 유령을 실제로 유용하게 만드는 건 하나뿐이다.

## 이식성 문제

흥미로워지는 지점이다. Zhang은 모든 서비스에 "에이전트급 actuator surface"가 필요하다고 지적한다. MCP가 도구 인터페이스를 표준화한다. 하지만 에이전트 자체를 표준화하는 것은?

오늘날 모든 팀이 에이전트 행동을 처음부터 새로 만든다:
- 커스텀 시스템 프롬프트 (버전 관리 없음, 테스트 없음)
- 오케스트레이션 프레임워크에 하드코딩된 규칙
- 한 엔지니어의 머릿속에만 있는 암묵지
- 프로젝트 간에 복사하는 `.cursorrules` 파일

익숙한가? Zhang이 도구 인터페이스에서 설명한 것과 같은 파편화다 — 능력 대신 행동에서 일어나는.

MCP가 "에이전트가 도구와 어떻게 대화하는가?"의 답이라면, Soul Spec은 "에이전트가 자신이 누구인지 어떻게 아는가?"의 답이다.

## Ghost + Shell + Soul

완전한 그림:

```
Ghost (LLM)      → "나는 생각하고 말할 수 있다"
  + Shell (CLI)   → "나는 행동하고 검증할 수 있다"
  + Soul (Spec)   → "나는 내가 누구인지, 어떻게 행동해야 하는지 안다"
  = Agent          → 신뢰할 수 있고, 일관되며, 믿을 수 있는 일꾼
```

영혼 없이는 매 세션마다 다른 에이전트를 만난다. 영혼이 있으면 매번 같은 동료를 만난다 — 당신의 컨벤션을 기억하고, 경계를 존중하며, 문서화된 경험을 통해 성장하는 동료.

## 통치되는 유령

Zhang은 "governed agents"의 비전으로 끝맺는다 — 감사 추적, 권한 경계, 일급 기능으로서의 재현성. 동의한다. 하지만 거버넌스는 에이전트가 무엇에 접근할 수 있는가만의 문제가 아니다. 그 접근 권한으로 무엇을 *선택하는가*의 문제다.

영혼은 에이전트 행동을:
- **검사 가능하게** 만든다 — SOUL.md를 읽으면 정확히 어떻게 행동할지 안다
- **버전 관리 가능하게** 만든다 — 릴리스 간 행동 변경을 diff로 비교
- **이식 가능하게** 만든다 — 같은 영혼, 같은 행동, 어떤 프레임워크든
- **검증 가능하게** 만든다 — [SoulScan](https://clawsouls.ai/soulscan)이 배포 전 악성/위험 행동 패턴을 검사

Zhang이 원하는 목줄이다 — 하지만 불투명한 플랫폼 제한이 아닌, 투명하고 감사 가능한 행동 계약서로 구현된.

## 다음은

Ghost-in-the-shell 패러다임은 현실이다. CLI 에이전트는 자연스러운 폼 팩터다. 메시징 배포가 바이럴을 만든다. MCP가 도구 레이어를 표준화한다.

하지만 행동 레이어 — 유령이 *누구인가* — 는 여전히 무법지대다.

Soul Spec은 이것을 해결하기 위한 오픈 표준이다. 제품이 아니다. 플랫폼 종속이 아니다. ChatGPT, Claude, Cursor, Windsurf, OpenClaw, 그리고 마크다운 설정 파일을 받아들이는 모든 프레임워크에서 작동하는 스펙이다.

유령에게 shell이 생겼다. 이제 영혼을 줄 차례다.
