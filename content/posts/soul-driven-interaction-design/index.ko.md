논문을 하나 공개했다: [*Soul-Driven Interaction Design: How Persistent AI Personas Create Self-Reinforcing Human-AI Feedback Loops*](https://doi.org/10.5281/zenodo.18675257). Zenodo에서 오픈 액세스로 읽을 수 있다.

핵심을 요약하면 이렇다.

## AI 페르소나는 "출력 스타일링"이 아니다

대부분의 사람들이 AI 페르소나를 꾸미기 정도로 생각한다. "간결하게 답해" 혹은 "친절하게 말해" — AI의 말투를 바꾸는 것. 거기서 끝.

우리가 주장하는 건 다르다.

AI에게 지속적 페르소나 — 우리가 **soul**이라 부르는 것 — 를 부여하면, AI의 행동만 바뀌는 게 아니다. **사용자의 행동이 바뀐다.** 의식적으로가 아니다. 인간이 대화 상대에 맞춰 무의식적으로 스타일을 조정하는 것과 같은 심리적 메커니즘이 작동한다.

이 말은 곧, 페르소나 설계가 화장(cosmetic)이 아니라 **인터랙션 디자인**이라는 뜻이다. 에이전트가 어떻게 말할지만 결정하는 게 아니라, 사용자가 어떻게 말할지를 설계하는 것이다.

## 피드백 루프를 만드는 네 가지 메커니즘

### 1. 대화적 미러링 (Conversational Mirroring)

언어학에서 오래 검증된 이론인 커뮤니케이션 조절 이론(Communication Accommodation Theory)에 따르면, 사람은 대화 상대의 스타일에 무의식적으로 맞춘다. 톤, 분량, 격식, 기술적 깊이 — 받는 대로 따라간다.

AI 상대로도 마찬가지다. "Surgical Coder" soul이 3줄짜리 코드 중심 답변을 주면, 사용자도 메시지가 짧아지고 기술적으로 정밀해진다. "Patient Mentor" soul이 따뜻하고 상세한 설명을 주면, 사용자는 더 길고 탐색적인 메시지를 쓴다. 같은 사람, 같은 작업. soul만 다르면 행동이 달라진다.

### 2. 기대 프레이밍 (Expectation Framing)

Soul이 프레임을 설정한다. "시니어 스태프 엔지니어" 페르소나는 암묵적으로 신호를 보낸다: *수준 높은 질문을 해라*. "참을성 있는 튜터" 페르소나는 다른 신호를 보낸다: *기초적인 질문도 괜찮다*. 사용자가 그에 맞춰 질문을 조정하고, 잘 조정된 질문은 더 나은 답변을 만들고, 그 답변이 프레임을 더 강화한다.

### 3. 컨텍스트 윈도우 강화 (Context Window Reinforcement)

여기가 흥미로운 부분이다. LLM은 대화 히스토리 전체를 기반으로 응답을 생성한다. 에이전트와 사용자가 특정 스타일(예: 간결하고 기술적)로 수렴하면, 대화 히스토리 자체가 그 스타일의 예시 모음이 된다. 이게 모델을 같은 방향으로 더 강하게 편향시킨다 — 원래 soul 설정만으로는 나오지 않을 정도로.

컨텍스트 윈도우가 **플라이휠**이 되는 것이다. Soul이 초기 방향을 설정하고, 사용자가 적응하고, 대화 히스토리가 그걸 고정한다.

### 4. 인지 부하 감소 (Cognitive Load Reduction)

일관된 페르소나가 있으면 매 턴마다 "이 AI는 어떤 녀석이지?"를 파악하는 정신적 비용이 사라진다. 에이전트의 성격을 내면화하고 나면 온전히 작업에 집중할 수 있다. 인간 동료와 오래 일하면서 호흡이 맞아가는 것과 같은 효율 향상이다.

## 실무에 시사하는 바

AI 에이전트를 설계하거나, 심지어 매일 쓰는 코딩 어시스턴트의 시스템 프롬프트를 고르는 것만으로도 이 프레임워크가 적용된다.

**"AI가 뭘 하길 원하는가?"만 묻지 말고, "사용자가 어떻게 행동하길 원하는가?"를 물어야 한다.**

간결한 soul은 짧은 답변만 만드는 게 아니다. 짧은 *대화*를 만든다 — 더 정밀한 입력, 더 빠른 작업 완료까지. 상세한 멘토 soul은 설명을 더 많이 하는 게 아니라, 사용자가 더 깊이 탐색하고, 후속 질문을 하고, 내용에 더 깊이 관여하는 공간을 만든다.

대부분의 사람이 아직 당기지 않는 디자인 레버다.

## Soul ≠ Prompt ≠ Skill

논문에서 처음부터 강조하는 구분:

- **프롬프트**는 일시적이다. 한 번의 인터랙션 스타일링.
- **Soul**은 지속적이다. 멀티 파일 아이덴티티 스펙(Soul Spec v0.3)으로, 시간에 걸쳐 모든 인터랙션을 형성한다.
- **Skill**은 에이전트가 *할 수 있는 것*. Soul은 에이전트가 *누구인지*.

우리가 설명하는 피드백 루프는 **지속성이 필수**다. 한 번의 대화로는 자기 강화적 행동 패턴이 만들어지지 않는다. Soul이 세션을 넘어 일관되게 존재해야 미러링, 프레이밍, 컨텍스트 강화가 복리로 쌓인다.

ClawSouls가 단일 시스템 프롬프트 대신 멀티 파일 Markdown 구조 — `SOUL.md`, `IDENTITY.md`, `STYLE.md`, `AGENTS.md` — 를 쓰는 이유다. 각 파일이 에이전트 아이덴티티의 다른 차원을 담당하고, Skill과 직교적으로 합성된다. 같은 git 워크플로우 Skill이라도 간결한 코더 soul과 조합하면 완전히 다른 인터랙션 패턴이 나온다.

## ClawSouls 현황

이 프레임워크를 실체화한 오픈소스 시스템:

- **Soul Spec v0.3**: 지속적 AI 페르소나를 정의하는 구조화된 Markdown 포맷
- **80개 이상의 soul**: 간결한 코더부터 창작 스토리텔러, MBTI 16유형까지
- **LLM 무관**: 시스템 프롬프트를 받는 모든 모델에서 동작
- **플랫폼 이동 가능**: CLI, 채팅, IDE 어디서든 같은 soul
- **Apache 2.0 라이선스**
- **SoulScan**: soul 패키지 보안 스캐닝 (공유 에이전트 설정이 공급망 공격 표면이 된다 — Snyk의 ToxicSkills 연구에서 샘플링된 스킬의 36%에서 프롬프트 인젝션 발견)

## 앞으로의 계획

논문은 한계를 솔직하게 밝힌다. 피드백 루프 모델은 확립된 이론(커뮤니케이션 조절 이론, CASA 패러다임)과 질적 관찰에 기반하지만, 통제된 실험은 아직이다. 피험자 내 설계(within-subjects) — 세 조건(soul 없음, 간결한 코더, 참을성 있는 멘토), 20-30명, 비교 가능한 코딩 과제 — 를 제안했고, 실행할 계획이다.

Soul Spec v0.5도 작업 중이다. **체화된 에이전트** — 로봇과 IoT 기기 — 로 스펙을 확장한다. 같은 soul, 다른 몸. 한 번 정의하고, 어디에든 구현한다(define once, embody anywhere).
