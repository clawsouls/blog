## 디지털 소울의 부상

OpenSouls(GitHub ⭐294)는 스스로를 "디지털 소울을 위한 NextJS + Vercel"로 포지셔닝하며 인상적인 런타임 엔진을 선보였습니다:

- **WorkingMemory**: 불변(immutable) 메모리 컬렉션
- **cognitiveSteps**: 메모리를 변환하고 타입 안정성이 보장된 응답을 반환하는 함수
- **MentalProcesses**: 행동 모드를 정의하는 상태 머신 (소개 → 추측 → 좌절 등)

신경과학과 심리학에서 영감을 얻은 구조였습니다. `@opensouls/soul` npm 패키지는 76번째 버전까지 출시되었습니다.

## 왜 사라졌을까?

정확한 이유는 알 수 없지만, 몇 가지 정황이 원인을 암시합니다:

### 1. 런타임 종속성
Bun 전용, TypeScript 전용. OpenSouls를 사용하려면 그들의 전체 기술 스택에 종속되어야만 했습니다. LLM 생태계가 엄청난 속도로 진화하는 상황에서, 특정 런타임에 종속되는 것은 큰 부담이 되었습니다.

### 2. 복잡성 vs 가치
WorkingMemory, cognitiveSteps, MentalProcesses... 배워야 할 개념이 너무 많았습니다. 반면, 대부분의 개발자는 잘 작성된 시스템 프롬프트만으로도 목표의 80%를 달성할 수 있다는 사실을 깨달았습니다. 나머지 20%를 위해 완전히 새로운 프레임워크를 배우는 것은 그만한 가치가 없었습니다.

### 3. 시장의 변화
"AI 캐릭터" 붐(Character.AI 시대)과 함께 시작되었습니다. 그러나 시장은 빠르게 **자율 에이전트와 도구 사용(Tool Use)** 중심으로 전환했습니다. 감정이나 성격 엔진의 중요성이 상대적으로 줄어들었습니다.

### 4. 불명확한 비즈니스 모델
오픈소스 엔진에 클라우드 호스팅을 결합한 모델이었지만, 개발자들은 LLM API를 직접 호출하는 방식을 더 선호했습니다. 굳이 미들웨어 계층을 추가할 이유가 없었던 것입니다.

## 우리가 얻은 교훈

Soul Spec은 근본적으로 다른 접근을 취합니다. OpenClaw 같은 프레임워크가 이미 확립한 선언적 파일 패턴을 따릅니다:

| | OpenSouls | ClawSouls |
|---|---|---|
| 접근 방식 | 런타임 엔진 (Node.js) | 선언적 스펙 (텍스트 파일) |
| 종속성 | Bun + TypeScript 필수 | 프레임워크 비종속 (Agnostic) |
| 학습 곡선 | 높음 (커스텀 SDK) | 낮음 (마크다운 파일) |
| 보안 | 없음 | SoulScan™ 자동 검증 |
| 상태 | 서비스 종료 | 활성, 80+ 소울 |

**핵심 통찰**: 페르소나는 **코드가 아닌 데이터**여야 합니다. 특정 SDK에 종속되는 것이 아니라, 어떤 프레임워크에서도 읽을 수 있는 텍스트 파일이어야 합니다. OpenClaw와 같은 현대적인 프레임워크들은 이를 이미 이해하고 있었으며, Soul Spec은 이를 이식 가능하고 검증 가능한 표준으로 공식화한 것입니다.

OpenSouls는 이러한 수요가 존재함을 증명했습니다. 다만, 그 구현을 위한 추상화 계층을 잘못 선택했을 뿐입니다.
